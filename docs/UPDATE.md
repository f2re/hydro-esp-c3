# Обновление и восстановление HydroESP-C3

У проекта есть три разные операции, и смешивать их нельзя:

```text
install     = первая USB-установка / явное задание Wi-Fi
              может применить WIFI_SSID/WIFI_PASSWORD из env/.env

deploy      = обычная повторная USB-прошивка
              никогда не меняет сохранённый Wi-Fi/NVS

wifi-flash  = повторная прошивка по Wi-Fi
              показывает прогресс и проверяет устройство после reboot
```

## Обычный повторный deploy по USB

После первой установки используйте:

```bash
./deploy.sh
```

Windows:

```powershell
.\deploy.ps1
```

`deploy` собирает и прошивает application image, но намеренно не передаёт в сборку `WIFI_SSID`, `WIFI_PASSWORD` или `WIFI_SEED_ID`. Поэтому локальный `.env` не может незаметно заменить сеть контроллера.

Для обновления текущей ветки перед прошивкой:

```bash
./deploy.sh --pull
```

## Обычное обновление по Wi-Fi

Узнайте IP на OLED и выполните:

```bash
./wifi-flash.sh 192.168.1.57
```

По умолчанию используется режим `auto`:

1. собирается OTA-safe `firmware.bin` без Wi-Fi provisioning flags;
2. проверяется текущий `/api/status`;
3. если HTTP жив — файл потоково передаётся в `/ota/upload` с прогрессом в терминале;
4. контроллер возвращает финальный `200 OK` / `OK`;
5. reboot выполняется отложенно, вне AsyncWebServer callback;
6. команда ждёт возвращения `/api/status` и проверяет новый `build`/uptime;
7. только после этого печатается **`OTA ПРОВЕРЕН`** и команда возвращает код `0`.

Типичный прогресс:

```text
[OTA] [########------------]  42%   520/1238 KiB  180.4 KiB/s
[OTA] [####################] 100%  1238/1238 KiB  176.9 KiB/s
[hydroctl] контроллер подтвердил приём прошивки; ожидаю перезагрузку
[hydroctl] OTA ПРОВЕРЕН: build abcdef12, uptime 3 s
```

Если соединение оборвалось **до передачи всего firmware.bin**, это ошибка. Если файл уже был передан целиком старой прошивке, но она перезагрузилась раньше финального HTTP-ответа, `wifi-flash` не делает преждевременный вывод: окончательным критерием остаётся возвращение контроллера с ожидаемым build.

### Выбор транспорта

HTTP и ArduinoOTA сохранены как два независимых канала:

```bash
# Автовыбор: HTTP штатно, ArduinoOTA как recovery
./wifi-flash.sh 192.168.1.57 --transport auto

# Только HTTP OTA
./wifi-flash.sh 192.168.1.57 --transport http

# Явно ArduinoOTA / espota.py, порт 3232
./wifi-flash.sh 192.168.1.57 --transport arduino
```

В режиме `--transport arduino` вывод `espota.py` не скрывается: в терминале виден его штатный интерфейс/прогресс передачи. То есть ArduinoOTA не удалён — он отделён от обычного HTTP-пути и доступен явно.

Можно отправить уже собранный application image:

```bash
./wifi-flash.sh 192.168.1.57 --file firmware.bin
```

Для внешнего `.bin` точный build заранее неизвестен, поэтому после reboot проверяется сам факт перезапуска и возвращения устройства.

## Web UI: загрузка прошивки

Раздел **Прошивка** в Web UI также сохранён. Он использует HTTP `/ota/upload` и показывает прогресс через browser XHR upload progress. ArduinoOTA не является браузерным протоколом, поэтому отдельной «ArduinoOTA-кнопки» в Web UI нет.

Оба HTTP-клиента — браузер и `wifi-flash` — используют один серверный endpoint и получают финальный ответ до отложенной перезагрузки.

## Независимый recovery ArduinoOTA

Актуальная прошивка постоянно обслуживает отдельный ArduinoOTA-канал на порту `3232`. Он не зависит от `/`, JavaScript или корректной выдачи Web UI.

Если HTTP-сервер сломан, `auto` пробует этот канал. Можно потребовать его явно:

```bash
./wifi-flash.sh 192.168.1.57 --transport arduino
```

Контроллер также публикует стандартный Arduino OTA service через тот же mDNS responder `hydro.local`. Поэтому среды, которые умеют искать сетевые Arduino-порты по `_arduino._tcp`, снова могут обнаруживать устройство; отдельный второй mDNS responder для этого не запускается.

Для диагностики и recovery всё равно надёжнее числовой IP с OLED: mDNS discovery зависит от конкретной локальной сети и клиента.

## OTA и локальный OLED

Во время прошивки насос принудительно выключается, scheduler и ручной старт не выполняются, а OLED перестаёт вращать обычные страницы.

Он показывает:

```text
ПРОШИВКА
  37%
[====      ]
```

После успешного `Update.end(true)` — **ГОТОВО / 100%**, после ошибки — **ОШИБКА / ПОВТОРИТЕ**. Перерисовка процентов ограничена, чтобы сетевые chunk-и не заставляли OLED мигать на каждом I²C обновлении.

Подробно: [OLED.md](OLED.md).

## Первая установка / смена Wi-Fi

Только для новой платы либо когда нужно намеренно записать другую сеть:

```bash
bash install.sh
```

Windows:

```powershell
.\install.ps1
```

`install` может брать Wi-Fi из окружения или `.env`. Это provisioning-сценарий, а не команда для повседневного повторного deploy.

Если Wi-Fi не подходит, контроллер после таймаута поднимает открытую сеть `HydroESP-Setup`; её адрес — `http://192.168.4.1`. IP текущего режима также выводится на OLED и в Serial.

## Один BIN для ручного прошивальщика

В GitHub Release есть файл:

```text
hydro-esp-c3-install.bin
```

Это единый полный образ для ручной прошивки с адреса `0x0`. Он нужен только для factory/recovery через сторонний flasher.

> [!IMPORTANT]
> Полный `install.bin` может заменить служебные области flash. Для работающего контроллера используйте `deploy`, `wifi-flash` или application OTA.

## Backup / restore

Перед заметными изменениями можно сделать backup:

```bash
python3 tools/hydroctl.py backup --host 192.168.1.57
```

Restore:

```bash
python3 tools/hydroctl.py restore hydroesp-backup.json --host 192.168.1.57
```

После restore плановая автоматика остаётся на паузе до явного возобновления.

Если Web UI не находится, см. [WEB_ACCESS.md](WEB_ACCESS.md).
