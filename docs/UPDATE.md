# Обновление и восстановление HydroESP-C3

У проекта три разные операции, и смешивать их нельзя:

```text
install     = первая USB-установка / явное задание Wi-Fi
             может применить WIFI_SSID/WIFI_PASSWORD из env/.env

deploy      = обычная повторная USB-прошивка
             никогда не меняет сохранённый Wi-Fi/NVS

wifi-flash  = повторная прошивка по Wi-Fi
             основной путь: HTTP /ota/upload
             резервный путь: независимый ArduinoOTA порт 3232
             после прошивки обязательно проверяет перезагрузку и build
```

## Обычный повторный deploy по USB

После первой установки используйте:

```bash
./deploy.sh
```

Windows:

```powershell
.\deploy.ps1
```

`deploy` собирает и прошивает application image, но намеренно не передаёт в сборку `WIFI_SSID`, `WIFI_PASSWORD` или `WIFI_SEED_ID`. Поэтому локальный `.env` не может незаметно заменить сеть контроллера.

Для обновления текущей ветки перед прошивкой:

```bash
./deploy.sh --pull
```

## Обычное обновление по Wi-Fi

Узнайте IP на OLED и выполните:

```bash
./wifi-flash.sh 192.168.1.57
```

или напрямую:

```bash
python3 tools/wifi_flash.py 192.168.1.57
```

Команда:

1. собирает текущую прошивку без Wi-Fi provisioning flags;
2. проверяет доступность контроллера и запоминает текущий build/uptime;
3. при доступном HTTP использует прямой `/ota/upload` — для этого сама Web-страница и JavaScript не нужны;
4. ждёт перезагрузку платы;
5. повторно читает `/api/status` и считает обновление успешным только после подтверждения нового build и перезагрузки;
6. если HTTP недоступен, использует независимый ArduinoOTA/espota канал `3232` как recovery-путь.

Это специально устраняет неоднозначность вида «плата уже обновилась, а терминал написал ошибку»: разрыв HTTP-соединения во время `ESP.restart()` сам по себе больше не считается провалом. Решение принимается по состоянию контроллера после перезагрузки.

Пример нормального результата:

```text
[hydroctl] controller online: build 1234abcd, uptime 3821 s
[hydroctl] Wi-Fi OTA: firmware.bin -> 192.168.1.57 via HTTP /ota/upload; Web UI page is not required
[hydroctl] firmware accepted; waiting for controller reboot
[hydroctl] OTA verified: controller is online, build 89abcdef, uptime 3 s
```

Можно отправить готовый application image без сборки:

```bash
python3 tools/wifi_flash.py 192.168.1.57 --file firmware.bin
```

Для произвольного `--file` build заранее неизвестен, поэтому подтверждается возврат контроллера после перезагрузки.

`hydro.local` поддерживается, но при диагностике надёжнее использовать числовой IP с OLED.

## Независимый recovery OTA 3232

Актуальная прошивка постоянно обслуживает отдельный ArduinoOTA-канал на порту `3232`. Он не зависит от страницы `/`, JavaScript или маршрута `/ota/upload`.

Обычно `wifi-flash.py` использует его только если HTTP-сервер недоступен. Чтобы принудительно проверить recovery-канал первым:

```bash
python3 tools/wifi_flash.py 192.168.1.57 --recovery-first
```

Чтобы разрешить только recovery-канал без HTTP fallback:

```bash
python3 tools/wifi_flash.py 192.168.1.57 --no-http-fallback
```

Вывод `espota.py` в штатном fallback-режиме перехватывается: временная недоступность UDP/3232 больше не должна выглядеть как финальная `[ERROR]`, если другой OTA-путь сработал и новая прошивка подтверждена. Для низкоуровневой диагностики есть `--debug`.

## Что происходит с OLED во время OTA

При начале любой OTA насос принудительно выключается. На время записи прошивки обычный цикл приложения не запускает расписание, кнопку ручного старта и стандартные страницы OLED поверх OTA-экрана. Поэтому дисплей остаётся на одном экране прогресса, а не переключается между часами/сетью и процентами прошивки.

После успешного `Update.end(true)` режим OTA остаётся зафиксированным до самого `ESP.restart()`, чтобы обычный экран не успел появиться на долю секунды перед перезагрузкой.

## Переход со старой прошивки

Старая прошивка может ещё не иметь recovery-порта `3232`, но `/ota/upload` обычно уже присутствует. Поэтому текущий `wifi_flash.py` использует HTTP как наиболее совместимый основной путь. Если HTTP недоступен, он пробует `3232`.

Если недоступны оба канала, один раз подключите USB и выполните `./deploy.sh` либо первичную установку с корректным Wi-Fi.

## Низкоуровневое HTTP OTA

Прямой старый способ сохранён:

```bash
python3 tools/hydroctl.py update --host 192.168.1.57 --file firmware.bin
```

Или для опубликованного GitHub Release:

```bash
python3 tools/hydroctl.py update --host 192.168.1.57
```

Он использует `/ota/upload`, но в отличие от `wifi_flash.py` не является основным диагностическим сценарием с обязательной post-reboot проверкой.

## Первая установка / смена Wi-Fi

Только для новой платы либо когда нужно намеренно записать другую сеть:

```bash
bash install.sh
```

Windows:

```powershell
.\install.ps1
```

`install` может брать Wi-Fi из окружения или `.env`. Это provisioning-сценарий, а не команда для повседневного повторного deploy.

Если Wi-Fi не подходит, контроллер после таймаута поднимает открытую сеть `HydroESP-Setup`; её адрес — `http://192.168.4.1`. IP текущего режима также выводится на OLED и в Serial.

## Один BIN для ручного прошивальщика

В GitHub Release есть файл:

```text
hydro-esp-c3-install.bin
```

Это единый полный образ для ручной прошивки с адреса `0x0`. Он нужен только для factory/recovery через сторонний flasher.

> [!IMPORTANT]
> Полный `install.bin` может заменить служебные области flash. Для работающего контроллера используйте `deploy`, `wifi_flash.py` или application OTA.

## Backup / restore

Перед заметными изменениями можно сделать backup:

```bash
python3 tools/hydroctl.py backup --host 192.168.1.57
```

Restore:

```bash
python3 tools/hydroctl.py restore hydroesp-backup.json --host 192.168.1.57
```

После restore плановая автоматика остаётся на паузе до явного возобновления.

Если Web UI не находится, см. [WEB_ACCESS.md](WEB_ACCESS.md).
